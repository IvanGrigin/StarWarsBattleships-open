# Star Wars Battleships — мастер-план цифровой реализации

Версия документа: 1.1  
Дата: 2026-09-13  
Статус исходного проекта: дизайн настольного прототипа; программная реализация отсутствует.

Этот документ предназначен для передачи другой нейросети или команде разработки. Он описывает не готовый код, а последовательность работ, границы модулей, рекомендуемые инструменты, форматы данных, тесты и критерии приёмки. Реализация должна выполняться небольшими проверяемыми задачами. Нельзя начинать сетевой или графический слой до появления однозначного симуляционного ядра.

---

## 1. Цель проекта

Создать пошаговую многопользовательскую 3D-тактику на гексагональном поле со следующими характеристиками:

- основной режим — четыре игрока, две команды по два игрока;
- поле — 61 гекс, то есть правильный гекс радиуса 4;
- корабль занимает один гекс и имеет одно из шести дискретных направлений;
- движение и поворот используют заряды;
- бой учитывает сектор, которым корабль обращён к противнику;
- корабли и герои описываются данными, а не зашиваются в код;
- клиент по умолчанию предназначен для Windows/macOS/Linux;
- тот же проект должен иметь оптимизированные Android/iOS-сборки;
- сервер является единственным источником истины;
- матч полностью воспроизводится по seed и журналу действий;
- любой человеческий игрок может быть заменён ботом;
- безграфический симулятор позволяет проводить массовые матчи;
- нейросетевые агенты обучаются через self-play и сравниваются с фиксированной лестницей ботов;
- баланс карточек измеряется автоматически.

### 1.1. Необходимые режимы

Обязательные для первой полной версии:

1. Локальная песочница для разработчика.
2. Матч против ботов без подключения к интернету.
3. Закрытая интернет-комната по коду.
4. Матч 2×2, где любое место может занимать человек или бот.
5. Повтор завершённого матча.
6. Безграфический пакетный прогон симуляций.

Дополнительные после стабильной версии:

- 1×1;
- один человек с ботом против двух людей;
- наблюдатели;
- открытый matchmaking;
- рейтинговый режим;
- пользовательские наборы правил и карточек;
- редактор карт;
- асинхронные матчи с длинным таймером.

### 1.2. Что не следует делать в первом релизе

- Не добавлять свободную физику полёта: положение корабля дискретное.
- Не синхронизировать клиентские 3D-transform как авторитетное состояние.
- Не обучать нейросеть по изображению экрана: агент должен читать состояние симулятора.
- Не дублировать правила отдельно в клиенте, сервере и Python.
- Не начинать публичный рейтинг до стабилизации правил и обработки reconnect.
- Не использовать оригинальные Minecraft-текстуры или чужие модели без разрешения.
- Не обещать математически идеальную игру нейросети без доказанной оценки exploitability.

## 3. Обязательные продуктовые решения до начала кода

Создать `docs/decisions/` и записывать каждое принятое решение отдельным ADR-файлом. Минимальный набор решений:

| ADR | Решение | Предлагаемое значение |
|---|---|---|
| ADR-001 | Лицензия и сеттинг | частный Star Wars-прототип либо собственный сеттинг для публикации |
| ADR-002 | Движок | Godot 4.x stable |
| ADR-003 | Языки и единый источник правил | Rust для canonical rules core и сервера; типизированный GDScript только для Godot-клиента; Python получает тот же Rust core через PyO3/maturin |
| ADR-004 | Рендерер | Mobile как основной профиль; Compatibility как fallback; Forward+ как desktop-enhancement |
| ADR-005 | Сетевая модель | выделенный авторитетный Rust-сервер; WSS/WebSocket для надёжного пошагового протокола |
| ADR-006 | Основной режим | четыре места, команды 2×2 |
| ADR-007 | Ориентация телефона | игровой матч только landscape; обе landscape-ориентации |
| ADR-008 | Правила информации | открытая информация, скрыт только будущий RNG |
| ADR-009 | Повторы и честность RNG | event log + периодические snapshots; hash-коммит seed в начале, раскрытие seed после матча |
| ADR-010 | ML-интерфейс | PettingZoo AEC-адаптер; RLlib опционально |
| ADR-011 | Offline-матчи | тот же Rust core в Godot через тонкий GDExtension bridge; обязательный Android/iOS spike до фиксации стека |

Нейросеть-разработчик не должна молча менять ADR. Изменение требует нового ADR с причиной, последствиями и планом миграции.

## 4. Формализация правил v3.0

### 4.1. Термины

Зафиксировать словарь:

- **матч** — вся партия до победы или ничьей;
- **команда** — два союзных игрока;
- **место/seat** — позиция игрока в порядке ходов;
- **раунд** — цикл, в котором каждый живой корабль получает одну активацию;
- **активация** — действия одного выбранного корабля;
- **действие** — движение, поворот, атака, способность или завершение активации;
- **заряд** — ресурс конкретного корабля;
- **направление** — целое число `0..5`;
- **сектор** — сторона корабля относительно цели: F, FR, BR, B, BL, FL;
- **гекс-расстояние** — стандартное расстояние в axial/cube-координатах;
- **событие** — подтверждённое изменение состояния, созданное ядром;
- **команда клиента** — запрос на действие, который сервер может отклонить;
- **ruleset** — версия правил и карточек с неизменяемым хешем.

### 4.2. Предлагаемая базовая структура матча

1. Создать матч с ruleset, секретным server seed и публичным seed commitment.
2. Назначить четыре места: `A1`, `B1`, `A2`, `B2`.
3. Провести драфт героев.
4. Провести драфт флотов.
5. Разместить корабли в стартовых зонах.
6. Начать первый раунд.
7. Игроки по очереди активируют ещё не активированный в раунде корабль.
8. Когда все возможные активации завершены, начинается новый раунд.
9. После каждого события проверяется уничтожение и условие победы.
10. При достижении лимита раундов матч завершается ничьей или по заранее заданному tie-breaker.

### 4.3. Предлагаемые правила драфта

- Один уникальный герой на игрока.
- Драфт героев змейкой: `A1, B1, A2, B2, B2, A2, B1, A1`, если когда-нибудь будет выбрано по два героя. Для первого релиза используется только первый круг.
- Три корабля на игрока.
- Не более одного корабля группы 2 у игрока.
- Корабли группы 2 уникальны в матче.
- Типы группы 1 могут повторяться между игроками, но не более двух одинаковых типов у одного игрока.
- «Фантом» нельзя выбрать; он появляется только из «Призрака».
- Неподписанное число на карточке временно трактуется как стоимость.
- Начальный тестовый бюджет: 17 очков на игрока.
- Значение бюджета является балансным параметром, а не окончательным правилом.

### 4.4. Предлагаемая структура активации

- Игрок выбирает один свой живой корабль, не активированный в текущем раунде.
- Корабль может выполнять легальные движения и повороты, пока есть заряды.
- Движение вперёд на один гекс стоит 1 заряд.
- Поворот на 60° влево или вправо стоит 1 заряд.
- Атака стоит 0 зарядов, но доступна не более одного раза за активацию.
- После атаки движение разрешено только если это отдельно подтверждено правилами. Для первой версии рекомендуется разрешить порядок действий свободно, но всё равно не более одной атаки.
- Игрок может закончить активацию с неиспользованными зарядами.
- В конце активации корабль восстанавливает 1 заряд, максимум 5.
- Если игрок не отправил команду до тайм-аута, сервер выполняет `EndActivation`.

### 4.5. Движение

- Поле использует pointy-top или flat-top ориентацию; выбрать один вариант в ADR и не смешивать формулы.
- Логические координаты — axial `(q, r)`, с производной cube-координатой `s = -q-r`.
- Гекс входит в поле радиуса 4, если `max(abs(q), abs(r), abs(s)) <= 4`.
- Направление корабля однозначно соответствует одному из шести соседних векторов.
- Движение возможно только в соседний гекс по текущему направлению.
- На одном гексе может находиться только один корабль или один блокирующий объект.
- Нельзя выходить за поле.
- Нельзя проходить сквозь корабль.
- Принудительное движение в недопустимую клетку отменяется, если карточка не задаёт столкновение отдельно.
- Поворот меняет только направление, не позицию.
- Визуальная анимация никогда не изменяет логическое состояние.

### 4.6. Базовый бой

1. Атакующий объявляет цель.
2. Ядро проверяет дальность, количество атак, принадлежность цели и специальные правила.
3. Вычисляется сектор атакующего в направлении цели.
4. Вычисляется сектор защищающегося в направлении атакующего.
5. Сервер создаёт броски d6 из детерминированного RNG.
6. Применяются пассивные модификаторы.
7. Открываются окна реакций героев в строго заданном порядке.
8. Итоговая сила каждого корабля ограничивается снизу нулём.
9. При равенстве урон отсутствует.
10. Проигравший получает разницу итоговых сил.
11. Урон сначала уменьшает щит, затем здоровье.
12. Создаются события урона, уничтожения и возможного превращения/воскрешения.
13. Проверяется конец матча.

Порядок модификаторов записать формулой:

```text
base die
 sector modifier
 permanent passive modifiers
 temporary status modifiers
 range modifier
 reaction-modified die
= final strength, minimum 0
```

Нужно явно определить, меняют ли Оби-Ван и Люк исходный кубик до добавления модификаторов или итоговую силу. Рекомендуется менять только грань исходного кубика.

### 4.8. Решения по особым кораблям

До реализации принять следующие точные контракты:

- **Призрак → Фантом:** Фантом появляется в той же клетке и ориентации, с полным HP, нулевым щитом и количеством зарядов, выбранным правилами. Рекомендуется сохранить текущие заряды, ограничив их максимумом Фантома.
- **Звезда Смерти:** определить hex-distance, линию видимости, сектор по направлению луча и штраф. Рекомендуемый первый вариант: `-2 × (distance - 1)`, чтобы соседняя атака не штрафовалась.
- **X-wing:** переписать способность целиком. Нельзя программировать исходную фразу. Один тестовый вариант: после ничьей при атаке 50% шанс нанести 1 урон; при победе работает обычный урон; при проигрыше бонуса нет.
- **Истребитель СИД:** только одна попытка воскрешения за экземпляр; при успехе остаётся на клетке с `d4 HP`, щит 0; событие уничтожения откладывается до результата попытки.
- **Дроид-стервятник:** если атакующий бросок равен 1, бросается d2; при успехе выполняется ровно один обязательный переброс, второй результат обязателен.

### 4.10. Конец матча

- Победа команды наступает, когда у соперника нет живых кораблей и нет отложенного воскрешения/превращения.
- Если последние корабли обеих команд уничтожены одной атомарной цепочкой событий, результат — ничья.
- Сдача одного игрока не завершает матч, если союзник продолжает; место сдающегося занимает бот или его корабли переходят серверному боту.
- Сдача всей команды завершает матч победой соперника.
- Для ботов и ranked-режима необходим настраиваемый `round_limit`.
- Tie-breaker по оставшемуся HP используется только если это явно включено ruleset; по умолчанию лимит даёт ничью.

## 5. Архитектура программного решения

### 5.1. Главное разделение

```text
Data definitions
       ↓
Rust deterministic rules core
       ↓             ↓                  ↓
Rust online server  PyO3 binding        Godot GDExtension bridge
       ↓             ↓                  ↓
       Godot client  PettingZoo/ML      Offline LocalMatchHost
```

Canonical реализация правил существует ровно в одном месте — Rust crate `game_core`. Сервер вызывает её напрямую, а Python получает те же типы и переходы состояния через PyO3/maturin. Godot-клиент не реализует правила повторно: сервер присылает публичный snapshot, события и набор легальных действий. Клиент может кэшировать эти данные для подсветки, но окончательное решение всегда принимает сервер.

Для offline human-vs-bots Godot загружает тонкий `game_godot_bridge`, который вызывает тот же `game_core` и предоставляет интерфейс `LocalMatchHost`, эквивалентный сетевому host по командам/событиям. До начала полной реализации выполнить build spike: одна core-функция должна собраться и запуститься на Windows, macOS, Linux, Android и iOS. Rust binding для Godot является community-зависимостью и его mobile-поддержка требует ранней проверки. Если spike не проходит, зафиксированный fallback — тонкий C ABI или C++ `godot-cpp` bridge к Rust core; переписывать правила на GDScript запрещено.

Такое разделение принято не ради преждевременной оптимизации. Без него план требовал бы либо медленно запускать Godot-процесс для каждого ML environment, либо переписать правила на Python и постоянно доказывать эквивалентность двух реализаций. Для массового self-play единый быстрый core важнее простоты первого прототипа.

Правила не должны зависеть от:

- Godot-сцен;
- кадровой частоты;
- анимаций;
- сетевых peer ID;
- локализованных строк;
- разрешения экрана;
- загруженных 3D-моделей.

## 7. Детерминированный симулятор

### 7.1. Обязательный API

```text
create_match(config, secret_seed)
clone_state(state)
get_active_agent(state)
get_legal_actions(state, agent)
validate_command(state, command)
apply_command(state, command) -> events, new_state
observe(state, agent)
is_terminal(state)
get_result(state)
serialize_snapshot(state)
restore_snapshot(bytes)
hash_state(state)
replay(revealed_seed, config, commands)
```

### 7.2. RNG и проверяемая честность

- Использовать один явно зафиксированный криптографический генератор в Rust core, например `ChaCha20Rng`, с закреплённой версией зависимости.
- Не использовать глобальный `rand()` движка, системное время или RNG клиента.
- Online-сервер получает 256-битный seed из OS CSPRNG; `seed_from_u64` для публичного матча запрещён.
- Перед матчем сервер публикует `SHA-256("swb-rng-v1" || seed_32_bytes || match_uuid_16_bytes || ruleset_hash_32_bytes)`. Поля имеют фиксированный размер и порядок, чтобы конкатенация была однозначной.
- Сам seed не передаётся клиентам до завершения матча: иначе клиент сможет предсказывать будущие кубики.
- Каждый случайный результат связан с seed и монотонным `rng_event_index`.
- Порядок потребления случайных чисел является частью ruleset.
- В событие `DieRolled` записывать тип кубика, индекс RNG и результат, но не внутреннее состояние генератора.
- После матча seed раскрывается и входит в подписанный replay; verifier проверяет начальный commitment и все броски.
- Для тренировочных матчей commitment не обязателен, но алгоритм и порядок RNG остаются теми же.
- Смена алгоритма RNG или порядка draws требует новой версии ruleset и replay schema.

Все авторитетные расчёты состояния используют целые числа. Float разрешён только в presentation, аналитике и входах нейросети. Выбор случайной грани кубика выполняется без modulo bias — через проверенный uniform range API закреплённой RNG-библиотеки. Canonical state hash использует фиксированный порядок полей, little-endian кодирование целых и зафиксированный hash-алгоритм.

### 7.3. Атомарность

Одна команда может создать цепочку событий, но состояние снаружи меняется атомарно. Например:

```text
DeclareAttack
  -> DieRolled ×2
  -> DieModified
  -> StrengthCalculated ×2
  -> ShieldDamaged
  -> HullDamaged
  -> ShipDestroyed
  -> ShipTransformed
  -> MatchEndChecked
```

Нельзя позволять клиенту вмешиваться посередине, кроме специально определённого окна реакции. Окно реакции оформляется отдельной фазой состояния с перечнем разрешённых команд и таймером.

### 7.4. Сокращение пространства действий

Для человека доступны микродействия. Для ботов дополнительно нужен генератор **планов активации**:

- перечислить все достижимые пары `(cell, facing)` при текущих зарядах;
- устранить циклы поворотов и маршруты с одинаковым результатом;
- для каждого результата добавить допустимую атаку/способность/пропуск;
- сохранить фактическую последовательность микрокоманд для применения сервером.

Это уменьшит ветвление поиска и позволит MCTS оценивать осмысленные ходы.

## 8. 3D-клиент и визуальная спецификация

### 8.1. Поле

- Тёмный фон с очень лёгкой туманностью или градиентом.
- Гексы логически лежат в одной плоскости.
- Основная сетка — один меш/один материал.
- Полупрозрачность сетки минимальна; пересекающиеся прозрачные слои запрещены.
- Подсветка доступных клеток делается отдельным инстансированным слоем.
- Центральный гекс и граница поля должны читаться при любом повороте камеры.
- Для команд использовать цвет плюс форму/иконку, чтобы не полагаться только на различение красного и зелёного.

### 8.2. Корабль

Логический transform строится только из:

- axial-координаты;
- высоты зависания;
- yaw = `direction × 60° + board_basis_offset`;
- визуального scale из asset metadata.

Движение анимируется между состояниями, но input блокируется или буферизуется до безопасной точки анимации. Серверное состояние применяется сразу; анимация только догоняет его.

У каждого корабля:

- LOD0/LOD1/LOD2;
- упрощённый selection mesh;
- bounding box;
- pivot в центре логического основания;
- объявленная передняя сторона;
- 1–2 общих материала по возможности;
- thumbnail;
- цветовой слой команды без дублирования модели.

### 8.3. Камера

Desktop:

- удержание средней/правой кнопки или клавиши + drag — orbit;
- колесо — zoom;
- WASD/стрелки или edge-pan — смещение фокуса;
- двойной щелчок по кораблю — фокус;
- клавиша возврата — центр поля;
- опциональная дискретная ротация на 60°.

Mobile:

- tap — выбор;
- drag по пустому полю — orbit;
- pinch — zoom;
- two-finger drag — pan;
- tap по выбранному кораблю — открыть действия;
- явные кнопки поворота влево/вправо;
- подтверждение опасного действия отдельной кнопкой;
- длительное нажатие — карточка/подробности;
- жест камеры никогда не должен случайно отправлять игровую команду.

Параметры:

- начальный азимут относительно места игрока;
- начальное возвышение 35–40°;
- диапазон возвышения примерно 25–60°;
- полный азимут 360°;
- ограничение zoom, чтобы всё поле нельзя было потерять;
- плавность камеры задаётся отдельно от логического tick.

### 8.4. UI матча

Обязательные элементы:

- активный игрок и команда;
- активный корабль;
- HP, shield, charge;
- герой и оставшиеся использования;
- кнопки легальных действий;
- доступные клетки и цели;
- шесть секторных значений;
- предварительный расчёт боя;
- таймер;
- журнал последних событий;
- меню сдачи/настроек;
- состояние подключения;
- режим просмотра карточки;
- доступная кнопка завершения активации.

UI не должен показывать нелегальное действие как доступное. Источник доступности — `legal_actions` ядра.

## 9. Desktop-first и мобильная оптимизация

### 9.1. Разрешения и ориентация

- Базовый UI проектировать для 1920×1080, но проверять от 1280×720.
- Окно desktop изменяемого размера, с минимальным безопасным размером.
- Матч на телефоне — landscape-only.
- Поддерживать обе landscape-ориентации через sensor-landscape/событие orientation change.
- Portrait во время матча показывает экран с просьбой повернуть устройство, не перестраивая 3D-бой целиком.
- Учитывать safe area, вырезы, закруглённые углы и системные gesture-зоны.
- UI строить anchors/containers, без абсолютных координат.
- Touch target — не менее примерно 44–48 логических пикселей.
- Текст и иконки масштабируются независимо от 3D render scale.

### 9.2. Профили качества

`Low Mobile`:

- Compatibility либо Mobile renderer по возможности устройства;
- 30 FPS target;
- 3D scale 0.59–0.67;
- минимальные частицы;
- без realtime GI;
- без теней у большинства объектов;
- LOD переключается рано;
- простые материалы;
- слабое или отсутствующее постобрабатывание.

`Medium Mobile`:

- Mobile renderer;
- 30/60 FPS option;
- 3D scale около 0.67–0.77;
- одна ограниченная directional shadow;
- средние частицы;
- более дальний LOD.

`Desktop`:

- 60 FPS target;
- scale 1.0;
- улучшенные тени и эффекты;
- Forward+ только как enhancement, не как требование правил/UI;
- расширенный particle budget.

`Desktop Low` должен визуально соответствовать мобильному baseline. Это предотвращает создание двух разных игр.

### 9.3. Предварительные бюджеты

Уточнить после выбора тестовых устройств:

- desktop frame: не более 16,7 ms при 1080p;
- средний mobile frame: не более 33,3 ms;
- high-end mobile: цель 16,7 ms;
- mobile resident texture budget: начальная цель до 256 MB;
- общее mobile memory: начальная цель до 500 MB;
- отсутствие frame spike более 50 ms при обычном ходе;
- вход в матч после lobby: до 10 секунд на среднем устройстве;
- reconnect до управляемого состояния: до 5 секунд при нормальной сети.

Бюджеты являются критериями измерения, а не поводом преждевременно ухудшать графику.

## 10. Буферизация изображений, моделей и эффектов

### 10.1. Категории ресурсов

`Always resident`:

- шрифты;
- основной UI atlas;
- placeholder-иконки;
- материалы поля;
- базовые эффекты выбора;
- модели/иконки текущего lobby.

`Match resident`:

- модели 12 выбранных кораблей;
- карточки четырёх героев;
- эффекты способностей, присутствующих в матче;
- звуки участвующих кораблей;
- arena environment.

`On demand`:

- подробные карточки невыбранных кораблей;
- высокодетальные LOD для replay/spectator;
- дополнительные косметические варианты.

### 10.2. Менеджер ресурсов

Реализовать `AssetCache` с функциями:

```text
request(asset_id, priority)
preload_match(manifest)
get_or_placeholder(asset_id)
retain(asset_id, owner)
release(asset_id, owner)
evict_to_budget(memory_budget)
get_progress(manifest)
cancel(manifest)
```

Требования:

- фоновые запросы через `ResourceLoader.load_threaded_request`;
- получение ресурса только после проверки статуса, чтобы не блокировать frame;
- приоритеты: UI/active ship > nearby ships > effects > detail cards;
- reference counting владельцев;
- LRU-вытеснение только ресурсов без владельца;
- placeholder вместо пустого/чёрного элемента;
- контролируемая очередь финального `load_threaded_get`/инстанцирования за кадр; реальный GPU upload внутри Godot профилируется, но не считается полностью управляемым публичным API;
- показ общего progress в lobby;
- отмена загрузки при выходе из комнаты;
- телеметрия времени IO, decode, GPU upload и memory delta.

### 10.3. Предзагрузка матча

1. Сервер завершает драфт.
2. Клиент получает `MatchAssetManifest` с ID и hash.
3. Клиент загружает LOD2 и thumbnails в первую очередь.
4. Затем LOD1, основные материалы и обязательные эффекты.
5. Клиент отправляет `AssetsReady(minimum_set_hash)`.
6. Сервер начинает матч, когда все клиенты готовы или истёк таймер.
7. LOD0 и необязательные эффекты могут догружаться после старта.

Нельзя держать сервер в зависимости от клиентской загрузки бесконечно. При тайм-ауте применяется согласованная политика: продолжить с placeholders, удалить клиента или заменить ботом.

### 10.4. Работа с изображениями

- Импортированные изображения загружать как Godot Resource, не через произвольный runtime filesystem path.
- UI-иконки объединять в atlas.
- Использовать mipmaps для 3D-текстур.
- Цветовые, normal и mask-текстуры импортировать с правильным color space.
- Не создавать новый `ImageTexture` каждый кадр.
- Для динамически обновляемой текстуры использовать `update`, а не повторное выделение памяти.
- Не хранить одновременно PNG source, распакованный Image и GPU Texture без необходимости.
- На мобильном избегать больших прозрачных изображений и нескольких перекрывающихся fullscreen-слоёв.
- Thumbnail-карточки иметь отдельного размера, не уменьшать 4K-изображение в UI.

### 10.5. Shader warm-up

- Составить небольшой warm-up scene со всеми вариантами базовых материалов и эффектов.
- Запустить её скрыто на loading screen или использовать pipeline cache движка.
- Не создавать уникальный shader на каждый корабль.
- Командные цвета передавать параметрами общего материала.
- Измерять первый показ взрыва, щита, мины и гиперпрыжка на слабом телефоне.

## 11. Minecraft → оптимизированная 3D-модель

### 11.1. Вход

Основной вход — `.schem` Sponge v3, созданный WorldEdit. Дополнительный вход — выделенная область Minecraft Java world через Amulet Core. Для первой версии поддержать только `.schem`; world-import добавить позже.

Для каждой постройки хранить manifest:

```json
{
  "id": "millennium_falcon",
  "source_file": "millennium_falcon.schem",
  "author": "...",
  "license": "...",
  "front_axis": "+z",
  "up_axis": "+y",
  "pivot_block": [0, 0, 0],
  "target_length_m": 8.0,
  "palette_id": "voxel_space_v1"
}
```

### 11.2. Импортёр

Шаги:

1. Прочитать размеры, palette, block states и block entities.
2. Проверить лимиты размеров до выделения памяти.
3. Нормализовать block state в внутренний `BlockVisualDefinition`.
4. Выдать отчёт о неподдерживаемых блоках.
5. Удалить воздух.
6. Удалить внутренние невидимые грани.
7. Объединить копланарные грани одинакового материала greedy meshing.
8. Обработать slabs/stairs/fences/glass отдельными шаблонами.
9. Разделить opaque/cutout/transparent поверхности.
10. Построить UV в собственный atlas.
11. Вычислить normals/tangents.
12. Сдвинуть к pivot и применить масштаб.
13. Создать LOD0.
14. Создать LOD1/LOD2 упрощением и/или более агрессивным meshing.
15. Создать selection/collision proxy.
16. Экспортировать GLB.
17. Запустить meshoptimizer/gltfpack.
18. Сохранить исходные atlases в lossless PNG/TGA и назначить Godot import profile: BPTC/BC на desktop, ASTC/ETC2 на mobile согласно выбранному renderer.
19. Опционально собрать KTX2/Basis Universal только для внешнего asset-bundle pipeline и включать его после автоматического Godot import/runtime smoke test.
20. Проверить glTF validator и отсутствие потери pivot/material metadata после `gltfpack`.
21. Создать asset report и thumbnails.

### 11.3. Правила оптимизации

- Не создавать один cube mesh на блок.
- Не создавать один material на тип блока.
- Предпочитать один atlas для opaque и один для cutout/transparent.
- Полностью прозрачные и внутренние поверхности удалять.
- Стекло использовать редко: прозрачность особенно дорога на телефонах.
- Мелкие детали, исчезающие на игровом масштабе, объединять или заменять цветом/normal map.
- LOD выбирать по экранному размеру, а не только по мировой дистанции.
- Реальный collision mesh не нужен: логическое столкновение происходит по гексам.

### 11.4. Автоматические ограничения

Каждый импорт формирует машинный отчёт:

- число исходных блоков;
- число видимых граней до/после meshing;
- triangles по LOD;
- количество материалов;
- количество textures и их размеры;
- GLB, исходных atlases и платформенных импортированных текстур file size;
- bounding box;
- unsupported blocks;
- предполагаемые draw calls;
- время импорта.

Сборка блокируется, если отсутствуют front/pivot/license metadata или модель не проходит validator.

## 12. Сетевой слой

### 12.1. Авторитетность

Клиент отправляет намерение:

```text
MoveForward(ship_id)
```

а не результат:

```text
SetPosition(ship_id, x, y, z)
```

Сервер:

1. аутентифицирует соединение;
2. проверяет match/seat;
3. проверяет sequence;
4. проверяет legal action;
5. применяет команду к ядру;
6. сохраняет события;
7. рассылает события;
8. периодически создаёт snapshot.

### 12.2. Протокол

- Один WSS/WebSocket connection с надёжной упорядоченной передачей, TLS и heartbeat.
- Gameplay, lobby и telemetry различаются типом сообщения и приоритетом в очереди. Физические отдельные каналы для пошаговой игры не нужны.
- Медленная telemetry не должна блокировать gameplay: её можно отбрасывать или отправлять отдельным HTTP batch.
- Версия протокола в handshake.
- Ruleset hash в MatchCreated.
- Максимальные размеры payload.
- Схемы всех сообщений.
- `command_id` предотвращает двойное применение после retry.
- `expected_sequence` обнаруживает устаревший клиент.
- Сервер не принимает RPC, которого нет в allowlist текущей фазы.

### 12.3. Reconnect

1. Клиент получает подписанный reconnect token.
2. При обрыве место резервируется на заданное время.
3. Сервер продолжает таймер или временно ставит матч на паузу согласно mode config.
4. Клиент подключается и сообщает последний event sequence.
5. Сервер отправляет snapshot и последующие события.
6. Клиент проверяет state hash.
7. Если игрок не вернулся, управление принимает серверный бот.
8. При возвращении правила режима определяют, можно ли вернуть управление человеку.

### 12.4. Mobile lifecycle

- Обрабатывать сворачивание приложения.
- Не считать краткое background-состояние немедленной сдачей.
- После resume выполнять health check и reconnect.
- Во время потери сети блокировать команды, но сохранять UI состояния.
- Не проигрывать накопленные анимации по одной: после reconnect можно перейти к snapshot и кратко показать сводку пропущенных событий.

### 12.5. Серверная инфраструктура

MVP:

- один Docker image;
- Rust `game_server`, использующий тот же `game_core`, что Python binding;
- один процесс может обслуживать несколько лёгких пошаговых матчей;
- lobby service и match worker допустимо держать вместе;
- активный state в памяти;
- replay/snapshot на диск или object storage;
- JSON structured logs;
- health endpoint;
- graceful shutdown с сохранением активных матчей.

После нагрузки:

- отдельный matchmaker;
- Redis только для coordination, не как источник правил;
- object storage для повторов;
- метрики Prometheus/OpenTelemetry;
- горизонтальное распределение матчей;
- региональные серверы.

## 13. Боты без нейросетей

### 13.1. Общий интерфейс

```text
BotPolicy.reset(match_info, seat_id)
BotPolicy.choose_action(observation, legal_actions, time_budget_ms)
BotPolicy.on_events(events)
BotPolicy.get_debug_info()
```

Бот запускается на сервере. Клиент не должен вычислять решение авторитетного бота.

### 13.2. Лестница сложности

`Bot L0 — RandomLegal`

- выбирает случайное легальное действие;
- нужен для fuzz и базовой проверки;
- никогда не отправляет незаконную команду.

`Bot L1 — GreedyDamage`

- перечисляет планы активации;
- вычисляет ожидаемый урон;
- атакует лучший доступный target;
- поворачивает наиболее сильный сектор к ближайшему врагу;
- избегает выхода под заведомо сильный ответный сектор.

`Bot L2 — TacticalHeuristic`

- utility: team HP/shield differential;
- focus fire;
- ценность сохранённых зарядов;
- ценность позиции и сектора;
- защита союзника;
- приоритет добивания;
- использование способностей по правилам;
- оценка следующей активации противника.

`Bot L3 — Expectiminimax`

- поиск на 1–3 активации;
- chance nodes для d6/d4/d2;
- coalition utility для двух команд;
- alpha-beta там, где применимо;
- transposition table по canonical state hash;
- iterative deepening по time budget.

`Bot L4 — MCTS`

- UCT/PUCT;
- sampled chance outcomes либо явные chance nodes;
- progressive widening для большого числа планов;
- эвристический rollout policy;
- повторное использование дерева между решениями;
- отчёт visits/value по кандидатам.

`Bot L5 — NeuralPolicy`

- загружает зафиксированный checkpoint;
- использует legal-action mask;
- при ошибке модели переключается на L2;
- runtime не зависит от компонентов обучения.

### 13.3. Аналитика боя для эвристик

Предварительно вычислить таблицу вероятностей для всех разумных пар итоговых модификаторов:

- вероятность победы/ничьей/поражения;
- ожидаемый урон атакующего;
- ожидаемый ответный урон;
- распределение разницы;
- влияние shield и вероятностных способностей.

Таблица должна генерироваться из правил автоматически, а не содержать ручные числа.

## 14. Обучение нейросетей и поиск стратегий

### 14.1. Среда обучения

Создать Python-адаптер PettingZoo AEC через PyO3 binding к тому же Rust `game_core`. Сетевой протокол для обучения не использовать: он добавит задержку и создаст второй путь исполнения. Среда должна поддерживать:

- последовательные действия четырёх агентов;
- две командные награды;
- фазы hero/ship draft;
- фиксированное максимум 12 ship slots;
- `alive/presence mask` для уничтоженных кораблей;
- маски легальных действий;
- seeded reset;
- headless batch execution;
- сохранение replay любого episode;
- environment conformance tests.

PyO3 binding должен предоставлять batch API (`reset_many`, `step_many`) и освобождать Python GIL на чистом Rust-расчёте. Сначала измерить single-core steps/sec, затем добавлять Rayon/process parallelism. Нельзя компенсировать медленный покомандный FFI миллионами Python-вызовов, не проведя профилирование границы.

### 14.2. Наблюдение

Рекомендуемое представление:

`Board tensor`:

- 61 гекс;
- occupancy;
- team/owner;
- ship type;
- facing one-hot 6;
- normalized HP/shield/charge;
- status/mine/bomb;
- legal destination flags.

`Entity table`:

- 12 фиксированных slots;
- presence/alive;
- type/group/cost;
- q/r;
- facing;
- HP/shield/charge;
- hero relation;
- activated/attacked flags;
- ability/status features.

`Global features`:

- phase;
- round;
- active seat/team;
- draft pool;
- remaining hero uses;
- round limit fraction;
- team totals;
- последние публичные события.

Все численные признаки нормализуются. Нельзя включать future RNG или внутренние данные оппонента, если они не являются публичной информацией.

### 14.3. Действия

Для первой обучаемой версии использовать стабильное пространство **микродействий**, совпадающее с командами ядра:

- выбрать доступный корабль фиксированного slot;
- `MoveForward`;
- `RotateLeft`;
- `RotateRight`;
- `Attack(target_slot)` для каждого из 12 фиксированных slots;
- `UseAbility(ability_slot, target_slot/cell_slot)` в заранее ограниченном формате;
- `EndActivation`;
- команды драфта по фиксированным индексам карточек.

Каждая позиция action vector всегда имеет одно значение во всех состояниях; недоступные действия закрывает mask. Это важно: динамический индекс «план №17» меняет смысл от хода к ходу и плохо обучается стандартными сетями.

Canonical activation plans остаются отдельным интерфейсом только для expectiminimax/MCTS. Продвинутая neural policy позже может стать иерархической: выбрать корабль → конечную позицию/ориентацию → цель → способность. Parametric candidate-action model допускается только после отдельного прототипа, где сеть получает признаки каждого кандидата, а не голый меняющийся индекс.

### 14.4. Награда

Базовая награда общая для команды:

- `+1` победа;
- `-1` поражение;
- `0` ничья.

Дополнительный shaping включается отдельным config и входит в rules/training hash:

- изменение разницы HP+shield;
- уничтожение/потеря стоимости флота;
- малая цена за затягивание;
- штраф за достижение лимита.

Shaping должен быть потенциальным или проверяться отдельно, чтобы агент не научился фармить урон вместо победы. Финальная оценка всегда проводится по sparse terminal reward.

### 14.5. Централизованное обучение

Рекомендуемый режим CTDE:

- actor получает наблюдение своего seat и legal mask;
- centralized critic видит полное публичное состояние обеих команд;
- союзники получают общую командную награду;
- политика может быть общей для всех seats с embeddings `seat/team`;
- отдельно сравнить две независимые team policies и одну shared self-play policy.

Если игра полностью открытая, actor тоже может видеть всё публичное состояние. CTDE всё равно полезен для credit assignment и командной координации.

### 14.6. Учебный curriculum

| Стадия | Сценарий | Условие перехода |
|---|---|---|
| C0 | один корабль против одного, без героев и драфта | уверенно побеждает L1 на симметричных сценариях |
| C1 | два корабля против двух, фиксированные флоты | ≥70% против L2 на отложенных seed |
| C2 | полный 2×2, фиксированные флоты | стабильная командная координация и отсутствие illegal actions |
| C3 | полный 2×2 с героями | ≥60–65% против смеси L2/L3 |
| C4 | полный драфт | не коллапсирует на несколько карточек без проверки |
| C5 | league self-play | растущий рейтинг против frozen pool |
| C6 | exploiter phase | чемпион устойчив к специально обученным контрполитикам |

Пороговые проценты являются начальными критериями и уточняются после получения доверительных интервалов.

### 14.7. Self-play league

Поддерживать:

- `main` — текущий кандидат;
- `past` — замороженные checkpoints предыдущих версий;
- `best` — текущий подтверждённый чемпион;
- `exploiters` — агенты, обученные находить слабость чемпиона;
- фиксированных L0–L4 ботов;
- несколько независимых training seeds.

Пример opponent sampling:

- 25% mirror current main;
- 50% frozen past/best;
- 25% exploiters и эвристические боты.

Каждый checkpoint хранит:

- model weights;
- observation/action schema hash;
- ruleset hash;
- training config;
- code commit;
- seeds;
- число environment steps;
- результаты evaluation;
- список известных слабостей.

### 14.8. Evaluation

- Training seed и evaluation seed никогда не пересекаются.
- Каждый кандидат играет обеими командами и на всех seats.
- Драфтовые варианты меняются парными seed.
- Минимум 2 000 матчей на важное сравнение либо расчёт требуемого sample size.
- Отчёт содержит 95% confidence interval.
- Одного win rate недостаточно: нужен matchup matrix.
- Чемпион заменяется только после прохождения фиксированной regression suite.

### 14.9. Поиск эксплойтов

Для каждого чемпиона:

- обучить минимум несколько exploiters с разными seed;
- для оценки joint best response дать exploiter-контроллеру управлять обоими seats одной команды; независимые seat policies дополнительно проверяются отдельно;
- дать им ограниченный, но одинаковый compute budget;
- измерить approximate best-response win rate;
- проверить rush, turtle, focus-fire, ability-combo и deliberate-draw стратегии;
- проверить политику против редких карточек;
- сохранять повтор каждого неожиданного поражения;
- автоматически кластеризовать причины поражений по draft и event patterns.

Если нижняя граница доверительного интервала exploiter win rate превышает установленный порог, чемпион не считается устойчивым.

### 14.10. Что означает «оптимальная игра»

Можно стремиться к:

- сильной политике относительно текущего ruleset;
- низкой измеренной exploitability;
- устойчивости против большого пула стратегий;
- приблизительному равновесию двух команд;
- лучшему решению в пределах заданного времени поиска.

Нельзя честно гарантировать:

- победу в каждой партии из-за случайных кубиков;
- нахождение точного Nash equilibrium в огромном пространстве состояний;
- отсутствие неизвестной контрстратегии;
- единственность оптимальной стратегии;
- использование всех карточек оптимальной политикой;
- совпадение машинно-оптимального и интересного человеку поведения;
- сохранение оптимальности после любого изменения правил.

Практическая формулировка цели: «агент превосходит фиксированную лестницу ботов, не проигрывает известным политикам лиги, имеет низкую approximate exploitability при заданном compute budget и подтверждает результат на закрытом наборе seed».

## 15. Балансировка

### 15.1. Собираемые метрики

- team win rate;
- win rate по каждому seat;
- first activation advantage;
- pick/ban rate корабля и героя;
- conditional win rate после выбора;
- стоимость флота;
- средний HP/shield damage;
- survival time;
- damage и survival на единицу draft cost;
- частота использования способности;
- value gained после способности;
- пары корабль–герой;
- пары союзных кораблей;
- matchup matrix флотов;
- длина матча и раунда;
- доля timeout/draw/stalemate;
- количество бесполезных активаций;
- средний branching factor;
- частота каждой ориентации/сектора в атаке;
- влияние RNG на результат;
- разница результатов людей и ботов после беты.

`Conditional win rate` нельзя напрямую считать силой карточки: сильные игроки/боты могут чаще выбирать конкретную карту, а доступность зависит от предыдущих picks. Отчёт обязан добавлять зеркальные драфты, paired seeds, seat controls и по возможности модель поправки на силу политики и состав флота. Простая корреляция получает пометку «диагностическая», а не «причинная».

### 15.2. Процесс изменения баланса

1. Зафиксировать проблему и подтверждающие метрики.
2. Создать гипотезу одного изменения.
3. Выпустить новый ruleset candidate.
4. Провести зеркальные матчи со старыми и новыми параметрами.
5. Использовать одинаковые seed и перестановки seats.
6. Рассчитать confidence intervals.
7. Проверить не только средний win rate, но и exploiters.
8. Просмотреть реплеи экстремальных случаев.
9. Принять или отклонить изменение.
10. Сохранить отчёт и причину решения.

### 15.3. Начальные автоматические гейты

Настраиваемые ориентиры:

- командная доля побед не дальше 5 процентных пунктов от 50% при симметричных условиях;
- seat advantage не выше 55% без объяснения;
- timeout/stalemate rate ниже 1%;
- ни одна доступная карточка не имеет почти нулевой выборки при оптимизированном драфте без отдельного review;
- карточка с conditional win rate вне 40–60% при достаточной выборке получает balance flag;
- новая версия не ухудшает champion exploitability сверх допуска;
- все статистические выводы содержат sample size и интервал, а не только процент.

Гейты не заменяют ручной дизайн: равновесная игра может быть скучной, затянутой или использовать только несколько доминирующих комбинаций.

## 16. Тестирование

### 16.1. Unit tests ядра

- axial/cube conversion;
- 61 уникальный гекс радиуса 4;
- соседние направления;
- distance;
- сектор по относительному направлению;
- повороты ±60° и полный цикл;
- расход/восстановление зарядов;
- занятая клетка и край поля;
- legality каждой команды;
- damage shield→HP;
- tie;
- negative modifiers;
- все кубики;
- каждая способность;
- уничтожение/воскрешение/превращение;
- командная победа/ничья;
- round limit.

### 16.2. Determinism tests

- одинаковый seed + команды → одинаковые события;
- одинаковый replay → одинаковый state hash на каждом шаге;
- snapshot/restore не меняет продолжение;
- разные desktop OS дают одинаковые логические hashes;
- Python adapter и server core согласованы на golden corpus;
- перестановка порядка сериализации словаря не меняет canonical hash.

### 16.3. Property/fuzz tests

- HP/shield/charge никогда не выходят за допустимые границы;
- два живых корабля не занимают один гекс;
- dead ship не получает действие;
- masked action действительно запрещён;
- legal action принимается;
- матч не зависает в фазе реакции без тайм-аута;
- случайные легальные партии завершаются либо достигают round limit;
- повторная команда с тем же ID не применяется дважды.

### 16.4. Network tests

- четыре клиента входят одновременно;
- поздний и двойной пакет;
- потеря соединения каждого seat;
- reconnect до/после snapshot;
- клиент с неверным ruleset/protocol;
- поддельная команда чужого корабля;
- команда не в свою фазу;
- server restart;
- бот принимает место;
- mobile background/resume;
- 3G/4G-like latency и packet loss simulation.

- Windows 10/11;

- минимум один Linux-дистрибутив;
- 1280×720, 1920×1080, ultrawide;

## 18. Безопасность и права

### 18.1. Сетевая безопасность

- Любой client payload считать недоверенным.
- Проверять тип, размер, диапазоны и ownership.
- Ограничивать частоту команд.
- Не десериализовать произвольные Godot-объекты из сети.
- Не позволять клиенту задавать RNG.
- Reconnect token должен быть ограничен матчем, seat и временем.
- Логи не должны содержать секреты и персональные данные.
- Guest ID и analytics ID разделить.
- Чат для первого MVP лучше не добавлять; он создаёт задачу модерации.

### 18.2. Импорт файлов

- Ограничивать размеры schematic, block count, palette и NBT depth.
- Обрабатывать неизвестные блоки без исполнения кода.
- Импорт выполнять вне игрового сервера.
- Выходные пути нормализовать, запрещать path traversal.
- GLB валидировать до добавления в bundle.

### 18.3. Интеллектуальная собственность

До публичного выпуска принять одно решение:

1. Получить необходимые права на Star Wars и используемые материалы; либо
2. Выпустить только частный некоммерческий прототип после юридической проверки; либо
3. Заменить названия, персонажей, внешний вид и lore собственным IP.

Для каждой Minecraft-постройки хранить автора и разрешение. Использовать собственные voxel-материалы, а не копии текстур Minecraft.

## 21. Протокол работы для другой нейросети

Перед каждой задачей нейросеть получает:

```text
TASK_ID:
Objective:
Allowed files:
Relevant rules/ADR:
Inputs/interfaces:
Exact deliverable:
Acceptance criteria:
Tests to run:
Forbidden scope:
```

Она обязана:

1. Прочитать только необходимые спецификации и интерфейсы.
2. Сначала подтвердить неизменяемые контракты.
3. Написать или обновить узкие тесты.
4. Реализовать только указанную задачу.
5. Не менять ruleset ради прохождения тестов.
6. Не добавлять зависимость без ADR.
7. Запустить заданные тесты и formatter.
8. Показать diff и результаты.
9. Перечислить допущения и нерешённые вопросы.
10. Не объявлять задачу завершённой при падающих тестах.

Шаблон запроса к кодирующей нейросети:

```text
Реализуй TASK B005: relative sector calculation.

Контекст:
- axial coordinates и direction 0..5 уже реализованы;
- arc order: F, FR, BR, B, BL, FL;
- цель всегда находится на соседнем гексе для этой задачи.

Результат:
- чистая функция определения сектора;
- unit tests всех 36 сочетаний facing × relative direction;
- без изменений UI, сети и карточек.

Критерии:
- поворот всей ситуации на 60° не меняет относительный сектор;
- полный набор тестов проходит headless;
- API и типы документированы.
```

После каждых 5–10 задач отдельный review-проход проверяет архитектурное расхождение, дублирование и тестовое покрытие.

## 22. Общая Definition of Done

Проект считается завершённым только если одновременно выполнено всё:

- правила v3 не содержат неразрешённых timing/target ambiguities;
- все 11 кораблей и 8 героев реализованы данными и тестами;
- четыре клиента завершают матч 2×2;
- любой seat может занимать человек, эвристический или neural bot;
- матч против ботов запускается offline на desktop и mobile через тот же canonical core;
- сервер не принимает незаконное действие;
- replay воспроизводится до одинакового state hash;
- reconnect возвращает правильное состояние;
- mobile background/resume не ломает матч;
- desktop 60 FPS и целевой mobile 30 FPS подтверждены профилированием;
- asset cache соблюдает memory budget и не создаёт заметных hitch;
- все корабли проходят `.schem → GLB → Godot platform texture imports` pipeline;
- touch UI работает в обеих landscape-ориентациях и safe areas;
- RandomLegal завершает массовые партии без illegal state;
- L1–L4 образуют измеримую лестницу сложности;
- neural champion проходит frozen evaluation suite;
- balance report воспроизводим из сохранённых seed и ruleset;
- exploiters не находят необработанную доминирующую стратегию в установленном бюджете либо проблема документирована;
- CI выпускает desktop/mobile/server artifacts;
- зависимости и контент проходят лицензионный review;
- существует rollback клиента, сервера и ruleset.
