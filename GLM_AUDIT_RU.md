# Самостоятельный аудит материалов GLM

Дата: 2026-09-13  
Аудитор: Codex, без повторного обращения к GLM.  
Объект: два ответа GLM, использованные как вспомогательные заметки при подготовке `MASTER_PLAN_RU.md`.

## 1. Что фактически сделал GLM

GLM получил две ограниченные задачи:

1. Найти неоднозначности настольных правил и предложить структуру детерминированного состояния.
2. Предложить раздел по ботам, self-play, обучению и измерению баланса.

Оба ответа технически завершились успешно, но достигли максимального лимита вывода. Вместо законченного результата GLM вывел главным образом процесс построения ответа и подробные заметки. Поэтому эти ответы нельзя считать готовой спецификацией, готовым кодом или независимо проверенным проектным решением.

В мастер-план попали только идеи, которые затем были сопоставлены с исходными PDF/TXT и переработаны. GLM не создавал и не проверял программный код.

## 3. Критические недостатки и исправления

### F-01. Не был выбран единый источник правил

**Проблема.** В заметках одновременно фигурировали Godot-ядро, Python-адаптер и сервер, но не было однозначно сказано, какой код является canonical. В таком виде другая нейросеть почти наверняка создала бы две реализации: GDScript для игры и Python для обучения. Они начали бы расходиться после первых изменений способностей.

**Риск.** Разные legal actions, RNG и timing в реальной игре и self-play. Балансные выводы тогда не относятся к выпускаемой игре.

**Исправление.** `MASTER_PLAN_RU.md` теперь выбирает Rust crate `game_core` как единственную реализацию переходов состояния. Rust-сервер вызывает crate напрямую; Python использует PyO3/maturin binding; Godot только отображает snapshot/events/legal actions.

**Статус:** исправлено.

### F-02. Динамический индекс полного плана плохо подходит RL

**Проблема.** GLM рекомендовал плоский список динамически перечисленных activation plans. Индекс `17` в одном состоянии означал бы одно действие, а в следующем — другое. Обычная policy head не получает стабильной семантики выходов. Обрезание списка также может удалять важную стратегию.

**Риск.** Плохая сходимость, зависимость от порядка перечисления, скрытая потеря легальных стратегий.

**Исправление.** Для первой neural среды принят фиксированный набор микродействий: select, move, rotate, attack по одному из 12 slots, ability, end. Маска меняется, значение индекса — нет. Полные activation plans оставлены expectiminimax/MCTS. Parametric action model разрешён только отдельным этапом с признаками кандидата.

**Статус:** исправлено.

### F-03. Seed нельзя раскрывать в начале сетевого матча

**Проблема.** Требование «replay = seed + actions» само по себе верно, но GLM не отделил тренировочный seed от публичного сетевого состояния. Если клиент знает seed и алгоритм, он способен предсказать будущие кубики.

**Риск.** Практический чит и недоверие к случайности.

**Исправление.** Сервер генерирует секретный seed, в начале публикует SHA-256 commitment, после матча раскрывает seed. Replay verifier проверяет commitment и все draws. Используется закреплённый `ChaCha20Rng`; seed не создаётся из времени через слабый `seed_from_u64`.

**Статус:** исправлено.

### F-04. Godot headless и ML throughput конфликтовали

**Проблема.** Запускать отдельный Godot-процесс или сетевой сервер для каждого PettingZoo environment возможно, но слишком дорого для миллионов коротких шагов.

**Риск.** Обучение ограничивается IPC/process overhead, а не логикой игры.

**Исправление.** Python загружает Rust core in-process через PyO3. Сетевой протокол в обучении не участвует.

**Статус:** исправлено.

## 4. Существенные технические замечания

### F-05. KTX2 нельзя объявлять обязательным без проверки Godot

**Проблема.** GLM правильно назвал KTX2 хорошим runtime-форматом, но из этого не следует, что конкретная версия Godot без дополнительных условий импортирует весь GLB+KTX2 pipeline именно так, как ожидается.

**Исправление.** Основной путь: lossless source atlas → Godot platform import → BPTC/BC для desktop и ASTC/ETC2 для mobile. KTX2 остаётся опцией внешних bundles только после smoke test.

**Статус:** исправлено.

### F-06. Сетевой транспорт не был выбран

**Проблема.** Были упомянуты «каналы», ENet и сервер без окончательного выбора. Для медленной пошаговой игры это избыточно и оставляет кодирующей нейросети слишком много свободы.

**Исправление.** Для MVP выбран WSS/WebSocket: надёжный, упорядоченный, хорошо работает через TLS и мобильные сети. Gameplay/lobby различаются логическими типами сообщений; отдельная ненадёжная телеметрия может отправляться HTTP batch.

**Статус:** исправлено.

### F-07. Approximate best response должен управлять всей командой

**Проблема.** В игре 2×2 exploiter одного seat не измеряет лучшую совместную контрстратегию команды.

**Исправление.** Главная проверка exploiter даёт одному team controller управление обоими seats. Дополнительно проверяется режим двух независимых actor policies, чтобы измерить цену ограниченной координации.

**Статус:** исправлено.

### F-08. Conditional win rate карточки не равен её причинной силе

**Проблема.** Сильный агент может чаще выбирать сложную карту; карта может быть доступна только на определённой позиции драфта. Простое `win rate when picked` смешивает силу карты, игрока, seat и состава.

**Исправление.** Требуются mirrored drafts, paired seeds, seat controls и поправка на силу policy/состав. Простая корреляция помечается как диагностическая.

**Статус:** исправлено.

### F-09. Управление GPU upload было сформулировано слишком уверенно

**Проблема.** Godot позволяет background resource loading, но публичный API не гарантирует точное дозирование каждого драйверного GPU upload.

**Исправление.** План ограничивает вызовы финализации и инстанцирования за кадр и требует измерять фактические hitch. Формулировка «полностью контролировать GPU upload» удалена.

**Статус:** исправлено.

### F-10. После выбора Rust core отсутствовал путь offline-игры на телефоне

**Проблема.** Отдельный Rust-сервер и Godot-клиент хорошо решают online-режим, но телефон не должен запускать второй локальный процесс. Без embedded bridge обязательный offline human-vs-bots режим оказался бы невыполнимым.

**Исправление.** Добавлен `game_godot_bridge` через GDExtension и единый `LocalMatchHost`. Поскольку godot-rust является community-проектом, а его Android/iOS tooling требует проверки, в M0 добавлен cross-platform build spike. Fallback — тонкий C ABI/godot-cpp bridge к тому же Rust core, но не новая реализация правил.

**Статус:** исправлено на уровне плана; технический риск должен быть закрыт spike-задачей A011.

### F-11. Детерминизм был заявлен без правил чисел и unbiased dice

**Проблема.** Слова «одинаковый seed» недостаточны, если core использует float, неоднозначную сериализацию или `% sides`, создающий modulo bias.

**Исправление.** Авторитетное состояние переведено на целые числа; зафиксированы порядок байтов и state hash; для кубиков требуется проверенный uniform range API. Python получает batch API с освобождением GIL, чтобы FFI не уничтожил throughput.

**Статус:** исправлено в спецификации.

## 5. Корректные, но требующие экспериментальной настройки идеи

Следующие пункты не являются ошибками, но их числа нельзя выдавать за доказанные:

- бюджет флота 17;
- пороги 70%, 60–65%, 55%;
- минимум 2 000 матчей;
- диапазон conditional win rate 40–60%;
- лимит draw/stalemate 1%;
- mobile memory 500 MB и texture budget 256 MB;
- 30/60 FPS профили;
- глубина expectiminimax 1–3 активации;
- доли opponent sampling 25/50/25.

В мастер-плане они должны оставаться начальными целями или настройками. После первого измерения throughput, variance и device baseline нужно создать ADR с обновлёнными значениями.

## 6. Нерешённые вопросы, которые GLM не мог решить из исходников

Это не следует отдавать кодирующей нейросети как право угадать:

1. Точная способность X-wing.
2. Заряды появившегося Phantom.
3. Формула дальности Death Star и линия видимости.
4. Полные правила мин и бомб.
5. Область действия Phasma.
6. Можно ли двигаться после атаки.
7. Стартовые зоны четырёх игроков.
8. Окончательный бюджет флота.
9. Разрешены ли повторы группы 1 у одного игрока.
10. Лимит раундов и таймер сетевой активации.
11. Целевые минимальные desktop/mobile устройства.
12. Статус Star Wars/Minecraft-контента для публикации.

Эти пункты должны быть закрыты на этапе M0 человеком-владельцем дизайна. До решения можно реализовать только интерфейс и тестовый ruleset с маркировкой `experimental`.

## 7. Аудит утверждения об «оптимальной игре»

GLM правильно отказался обещать постоянную победу, но критерий нужно формулировать строго.

### Что возможно проверить

- win rate против L0–L4 на закрытых seed;
- результат против frozen league;
- результат совместного team exploiter;
- approximate exploitability при зафиксированном compute budget;
- устойчивость к rush/turtle/focus-fire/draw policies;
- воспроизводимость evaluation;
- confidence interval результата;
- точный best move для маленьких урезанных сценариев, решаемых полным перебором.

### Что невозможно заявлять без доказательства

- «агент играет абсолютно оптимально»;
- «агент всегда выиграет»;
- «не существует неизвестной контрстратегии»;
- «50% mirror win rate означает Nash equilibrium»;
- «высокий Elo означает баланс всех карточек»;
- «оптимальная для бота стратегия будет интересной людям».

Для небольших подзадач нужно создавать exact-solver fixtures: один-два корабля, ограниченное число ходов, перечислимые chance outcomes. На них search/neural policies сравниваются с точным решением. Для полной игры используется только приближённая оценка.

## 8. Итоговая оценка GLM

| Область | Оценка |
|---|---|
| Поиск пробелов правил | сильный первый проход |
| Полнота законченного deliverable | неудовлетворительно: оба ответа оборвались по лимиту |
| Архитектура единого core | недостаточно определена |
| Боты до ML | хорошо |
| Self-play/evaluation | полезно, но требовало командных уточнений |
| Мобильная/asset часть | поверхностно и местами чрезмерно уверенно |
| Готовность для прямой реализации | до аудита — низкая; после исправлений — пригодна как мастер-план, но M0-решения остаются человеческими |

Итог: GLM был полезен как генератор проверочного списка, но не как архитектор или финальный верификатор. Его материалы нельзя передавать кодирующей нейросети без исправлений, перечисленных выше.
