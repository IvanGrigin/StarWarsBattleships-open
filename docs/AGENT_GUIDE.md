# Полное руководство для AI-агентов и разработчиков

Этот файл — единая инструкция по работе над проектом: с чего начать, где что
лежит, как менять код и данные, как проверять, как оформлять коммиты и
присылать работу. Краткая выжимка — в `AGENTS.md`; при расхождении прав тот
документ, что строже.

## 1. Что это за проект

«Эпохи и фракции» — пошаговая тактика на гексах по мотивам домашней настольной
игры: два игрока собирают флот (герой и три корабля) и сражаются на поле
радиуса 4. Некоммерческий фанатский прототип.

- Актуальная играбельная версия — **v4**, каталог `tools/play_v4/`
  (сервер на Python, интерфейс на three.js). Все новые работы — в ней.
- `demo/`, `browser-demo/`, `rust/game_core/`, `src/` — прототип v3.5 и его
  ядро. Не основа для новых работ; трогать только по прямой задаче.

Владелец проекта — единственный, кто принимает решения о правилах, балансе,
версиях и публикации. Агент предлагает и выполняет; спорное — спрашивает.

## 2. Первый запуск

```bash
gh repo fork IvanGrigin/StarWarsBattleships-open --clone   # свой форк
cd StarWarsBattleships-open
git config core.hooksPath .githooks                        # проверки коммитов и push
unzip -o data.zip                                          # ассеты от владельца (если их ещё нет)
python3 tools/check_assets.py                              # всё ли на месте
python3 tools/play_v4/server.py --cards --port 8767        # игра: http://localhost:8767/
```

Нужны: Python 3.12+ (пакеты Pillow, numpy, scikit-learn — для GIF и
оптимизатора баланса), Node.js (проверка синтаксиса JS), для полного набора
тестов — Rust и Godot 4.7. В полном комплекте от владельца ассеты уже лежат
на местах.

## 4. Порядок работы

1. Прочитать задачу, затем код, который она затрагивает, целиком — до правок.
2. Работать в ветке своего форка. В `main` общего репозитория напрямую не
   пушить; долгоживущие ветки в общем репозитории не заводить.
3. Делать законченные небольшие шаги; каждый шаг — проверка, затем коммит.
4. К каждой заметной работе — запись в `docs/V0.5_DESIGN.md`: что сделано,
   какое решение владельца за этим стоит, что проверено и что нет.
5. Перед pull request: `bash tools/run_ci_tests.sh`, `git fetch upstream`,
   `git rebase upstream/main`, при занятых номерах — перенумеровать коммиты.
6. Pull request в `main` общего репозитория. В описании: что изменено, как
   проверено, что осталось непроверенным.

Чужие незакоммиченные файлы и результаты других агентов принадлежат владельцу:
не удалять, не перезаписывать, не коммитить без его слова. Перед удалением или
слиянием — проверить точные пути и сохранить восстановимую копию.

## 5. Коммиты

Формат обязателен, его проверяют хук `commit-msg` и CI
(`tools/check_commit_message.py`). Полные правила — `docs/AI_COMMIT_POLICY.md`.

```text
v0.5.1.00003/Claude: краткое описание результата

Время: 2026-10-10T12:30:00+02:00
Что: Конкретно, что изменено — файлы, поведение, проверки.
Почему: Причина или решение владельца, ради которого это сделано.
```

- `v0.5.1` — линия версий; меняет её только владелец.
- `00003` — следующий по порядку номер в `main`, без пропусков и повторов.
  Узнать последний: `git log upstream/main --format=%s -1`.
- После косой черты — исполнитель: ровно `Claude`, `GLM` или `Codex`.
- `Время` — ISO 8601 до секунд с часовым поясом. Удобно:
  `date +%Y-%m-%dT%H:%M:%S%z | sed 's/\(..\)$/:\1/'`.
- Автор Git в открытом репозитории — служебный адрес GitHub
  (`ID+login@users.noreply.github.com`), не личная почта.
- Обходить хуки (`--no-verify`) нельзя. Хук не поддерживает `--amend`
  единственного коммита: вместо правки — новый коммит.
- Историю `main` не переписывать, force-push не делать.
- Один коммит — одна законченная мысль. В коммит не должны попадать чужие
  файлы, ассеты, кэши и личные данные.

## 6. Проверки

```bash
bash tools/run_ci_tests.sh        # всё: данные, Python, синтаксис JS, Rust, Godot
python3 tools/validate_v4.py      # быстро: карточки v4
python3 tools/check_assets.py     # ассеты на месте
```

Тот же набор запускают хук `pre-push` и GitHub Actions (`Project tests`,
`AI commit policy`). Красный статус — не сливать.

`node --check` не ловит все ошибки ES-модулей (например, повторное объявление
имени в одной функции). Надёжнее:

```bash
node --input-type=module -e "$(sed 's/^import .*$//' tools/play_v4/game.js)" 2>&1 | grep -iE "syntax|already"
```

### Проверка в браузере

- **Только на своём порту** (`--port 8767` и т. п.). На 8766 может играть
  владелец: состояние партии на сервере одно, чужой клик сделает ход в его игре.
  Чужой сервер не перезапускать — это сбрасывает партию.
- **Без звука.** Он выключен по умолчанию; не включать при проверках.
- Вкладка в фоне почти не рисует кадры (`requestAnimationFrame` стоит), и
  CSS-анимации тоже. Для проверки есть `window.__swb.debugFrame()` — рисует
  кадр вручную; `window.__swb` даёт сцену, камеру, жетоны, эффекты, колодец.
- Интерфейс подгружает скрипты с номером версии (`game.js?v=…` в `index.html`).
  После правки JS или CSS — менять этот номер, иначе браузер возьмёт старый файл.
- Сообщать честно: что увидено своими глазами, а что проверено только
  отсутствием ошибок.

## 7. Как менять правила и баланс

Правила — только в `tools/sim_v4/rules.py`. Сервер и боты используют один и тот
же `Match`, поэтому правило, сделанное «только в интерфейсе», — ошибка.

- Любое изменение состояния партии должно входить в `Match.snapshot()` и
  `restore()`: боты «примеряют» ходы на снимке, и забытое поле ломает партию
  (так однажды проскакивал номер раунда).
- Новое правило — сразу научить ему ботов (`bots.py`: перебор `plans` и оценка
  `score_here`/`evaluate`), иначе бот будет играть против собственных интересов.
- Числа кораблей и героев: править `tools/gen_v4_dataset.py` и
  `data/balance/v4_patch.json`, затем
  `python3 tools/gen_v4_dataset.py && python3 tools/validate_v4.py`.
  Файлы в `data/rulesets/v4/` руками не редактировать.
- Решения владельца, действующие сейчас: у кораблей меняются только числа
  (сектора, щит, корпус, цена), фракции — нет; способности героев не меняются,
  меняется цена героя в драфте; эпоха партии выбирается до драфта.
- Баланс проверять симуляцией, а не на глаз: сотни партий ботов, доля побед
  стороны и карточки. Пример — раздел про «Призрака» в `docs/V0.5_DESIGN.md`.
- Долгие расчёты запускать модулем из `tools/` (`python3 -m sim_v4.full_run …`),
  не через stdin: пул процессов, запущенный иначе, зависает и греет машину.
  По окончании — убедиться, что процессы завершились.

## 8. Как менять интерфейс

- Клик по полю: свой мигающий корабль — начать его ход; светящаяся клетка —
  полёт; враг под огнём — прицел, второй клик — выстрел. Остальное — кнопками
  в панели внизу поля. Вместо окон «вы уверены?» — отмена (`⌘Z`).
- Каждое частое действие — один клик или одна клавиша. Прежде чем добавить
  кнопку, проверить, нельзя ли убрать шаг.
- Все события боя сервер отдаёт списком `fx` со снимком позиций; интерфейс их
  проигрывает. Новое событие правил — добавить в `fx`, а не угадывать на клиенте.
- Эффекты и декорации не должны перехватывать клики и влиять на правила.
- Уважать `prefers-reduced-motion`: тяжёлые анимации отключаются.
- Поворот каждой модели размечен владельцем и запечён в GLB. Не «исправлять»
  ориентацию кодом (укладывать, разворачивать) — править разметку.

## 9. Модели и ассеты

- В git — только текстовые описания (`index.json`, `manifest.json`, README).
  Картинки, модели, текстуры и аудио в git не добавлять: их папки в `.gitignore`.
- Игровые модели: `demo/assets/models/v4/<корабль>.glb`. Источник, автор,
  лицензия и поворот — в `index.json`.
- Все скачанные модели-кандидаты — `assets_source/external_models/raw_candidates/`
  (в комплекте — облегчённые копии `_preview/`, оригиналы по 100–860 МБ у владельца).
- Переразметка: `python3 tools/model_preview/serve.py`, страница
  `http://localhost:8765/tools/model_preview/index.html`; номера игровых
  моделей — `tools/model_preview/IN_GAME_MODELS.md`. Перенос в игру:
  `python3 tools/model_preview/export_game_models.py <корабль>`.
- Новый ассет: файл — владельцу в архив, строка в `docs/ASSETS.md` и
  `LICENSES.md` (путь, автор, источник, лицензия). Код обязан работать и без файла.
- Без записи о лицензии ассет не добавлять. Чужие токены и пароли не вводить,
  защиту от ботов на сайтах не обходить.

## 10. Права и публикация

- Иллюстрации — арт и кадры по «Звёздным войнам» (Lucasfilm Ltd.), временные
  заглушки. У части моделей запрещено коммерческое использование или
  производные работы. Текстуры планет нельзя раздавать отдельными файлами.
- Поэтому: ассеты не публиковать, в открытый репозиторий не класть, в
  скриншоты и записи для публикации не включать без решения владельца.
- Лицензия на код не выбрана — все права сохранены.
- Личные данные (почта, пути домашней папки, адреса сети) в репозиторий не
  попадают; перед коммитом — `git grep -n "/Users/"`.

## 11. Как отчитываться

- Сначала итог: что сделано и работает ли. Затем — что проверено и как.
- Провал теста — сказать прямо и показать вывод. Пропущенную проверку — назвать.
- Не выдавать «код без ошибок» за «видел, что работает».
- Числа — с тем, что они измеряют, и на скольких партиях получены.
- Найденную попутно ошибку — исправить в корне и описать, а не обходить.
- Решения за владельца не принимать молча: версия, публикация, удаление,
  изменение правил — спросить или явно пометить как своё предложение.
