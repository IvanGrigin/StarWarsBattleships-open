# ADR-012: Особые правила кораблей (C007–C011) — контракты, порядок кубиков, расширение состояния

Дата: 2026-09-13. Статус: принято.

## Контекст

Спринт 1 сознательно отключил особые способности (ADR-011): формулировки карточек были неоднозначны, а открытые вопросы rules-v3 §9 отложены до M2. Волна 3 (задачи C007–C011 из MASTER_PLAN_RU.md §20, EPIC C) реализует пять особых правил кораблей поверх зелёного движка. Мастер-план §4.8 фиксирует точные контракты; этот ADR переводит их в норматив для кода и данных, фиксирует спорные трактовки и разрешает расширение canonical-состояния (core-api §7 — имена ключей pin, расширение только через ADR).

Затронутые правила карточек (rules-v3 §9.1–9.5): Призрак → Фантом, дальний выстрел Звезды Смерти, «спорный шанс» X-wing, воскрешение истребителя СИД, переброс дроида-стервятника.

## Решения

### 1. Механизм данных — существующее поле `abilities`

Способности включаются данными через уже существующее поле `abilities` карточек кораблей: `{"id": "<идентификатор>", "enabled": true}`. Новое верхнеуровневое поле (например, `special`) не вводится, потому что `data/schemas/ship.schema.json` запрещает неописанные свойства (`additionalProperties: false`). Схема при этом разрешает `enabled: boolean` и дополнительные поля внутри объекта способности — используется готовый параметр `"transform_to": "phantom"` у Призрака.

Идентификаторы способностей сохранены такими, как они уже зафиксированы в rules-v3 §9 и данных карточек (переименование сломало бы документы и данные без пользы):

| Корабль | ability id | Правило |
|---|---|---|
| `ghost` | `transform_to_phantom` | C007 |
| `death_star_1` | `ranged_shot` | C008 |
| `xwing_t65` | `lucky_shot` | C009 |
| `tie_fighter` | `resurrection` | C010 |
| `vulture_droid` | `reroll_one` | C011 |

Движок читает только способности с `"enabled": true`; будущие правила добавляются данными без изменения движка. Включение способностей меняет `ruleset_hash` (CardStore хеширует содержимое `ships/*.json`) — это ожидаемое следствие по ADR-011 («новая версия ruleset с новым hash»). `tools/validate_data.py` (DATA) снимает защиту ADR-011 при наличии этого ADR.

### 2. Порядок потребления кубиков (pin)

Порядок — часть правил (core-api §2/§9). В одной атаке:

1. Бросок атакующего d6.
2. Если атакующий — `vulture_droid` и выпал 1: d2; успех (2) → ровно один обязательный переброс d6, второй результат финален, даже если снова 1 (повторов нет). Неудача (1) → остаётся 1.
3. Бросок защищающегося d6.
4. Силы `max(0, die + arc)` (у атакующего — минус дальнобойный штраф, см. §3), сравнение. При ничьей, если атакующий — `xwing_t65`: d2; успех (2) → защитник получает ровно 1 урон (сначала щит). Неудача → урона нет. Победа/поражение X-wing — обычный конвейер без бонуса.
5. При уничтожении проигравшего: `ghost` → `ShipTransformed` без кубика; `tie_fighter` (первое уничтожение) → d2; успех → d4 и воскрешение; неудача → обычный `ShipDestroyed`.

Каждый бросок потребляет match-RNG, `rng_index` монотонно с 0 в порядке бросков, `rng_counter` увеличивается на число фактических вызовов `next_die`. Роль (`role`) в `DieRolled` — сторона, которой принадлежит бросок: вспомогательные кубики стервятника и X-wing — `"attacker"`, кубики воскрешения — сторона уничтожаемого корабля (`"attacker"`, если проиграл атакующий, иначе `"defender"`).

### 3. C008 — дальний выстрел Звезды Смерти

- `DeclareAttack` для `ranged_shot` разрешён на живого врага на **любом расстоянии** в пределах поля; для остальных кораблей ошибка `not_adjacent` сохраняется.
- Штраф атакующему: `−2 × (distance − 1)` к **итоговой** силе, то есть `total = max(0, max(0, die + arc) − 2·(d−1))`; соседняя атака (d = 1) не штрафуется.
- Секторы обеих сторон считаются по направлению луча: атакующего — `direction_from(att, tgt)`, защитника — `direction_from(tgt, att)`.
- **Линия видимости не блокируется кораблями** (v3 — открытый космос; ни документ, ни карточка не вводят понятие блокировки).
- Направление луча для не-соседних клеток определено так (точная и целочисленная арифметика, без float): для соседей и клеток на точном гекс-луче — `direction_from`; иначе направление с максимальной проекцией смещения на единичный вектор направления. Плоские координаты pointy-top: `x = √3·(q + r/2)`, `y = 3r/2`; при подстановке `X = 2q + r` проекция смещения `(dq, dr)` на дельту направления `(a, b)` равна `(2·dq + dr)·(2a + b) + 3·dr·b` с точностью до положительного множителя; длины всех шести направлений равны, поэтому сравнение точное. Ничья по проекции → меньший индекс направления. Определение детерминированно и платформонезависимо.
- Событие `StrengthCalculated` атакующего дополнено полем `range_penalty` (int; 0 для обычных атак и у защищающегося): `total = max(0, die + arc_bonus − range_penalty)`.

### 4. C007 — Призрак → Фантом

При уничтожении `ghost` корабль **не умирает**: та же клетка, ориентация и `ship_instance_id`, `type_id` становится `"phantom"`, `hp = max_hp` фантома (2), `shield = 0`, `charges = min(текущие заряды призрака, max_charges фантома)`. Событие: `ShipTransformed {ship_instance_id, from_type, to_type, hp, shield, charges}`; `DamageApplied` излучается до него. Кубиков превращение не потребляет. Фантом — обычный корабль: его уничтожение финально и повторного превращения не вызывает. Активация атакующего, превратившегося в фантома посреди своего хода, продолжается (корабль жив). Команда считается уничтоженной только когда живых кораблей нет — живой фантом держит команду в игре (проверка конца матча считает `alive`).

### 5. C010 — воскрешение истребителя СИД

- При первом уничтожении `tie_fighter` (только от боевого урона) бросается d2: успех (2) → корабль **остаётся на клетке** с `hp = d4`, `shield = 0`, `alive = true`, событие `ShipRevived {ship_instance_id, hp}`; неудача → обычный `ShipDestroyed`.
- Попытка одна за экземпляр за матч: флаг `revive_used` выставляется в `true` в момент попытки **независимо от исхода**; второе уничтожение финально без d2.
- Событие `ShipDestroyed` **откладывается** до результата попытки: до броска ничего об уничтожении не излучается.
- Проверка конца матча выполняется после разрешения попытки — воскрешение может спасти команду от поражения в тот же ход.

### 6. C009 — X-wing, «спорный шанс минимального урона»

Формулировка карточки программируется по MASTER_PLAN §4.8 целиком: бонус работает **только при ничьей**, только когда X-wing — атакующий: d2, успех → ровно 1 урон защитнику (сначала щит; урон может уничтожить цель — тогда применяются её собственные посмертные правила C007/C010). Не требует флагов состояния.

### 7. Расширение состояния (core-api §7, версия остаётся 1)

- Каждый корабль при создании получает `"revive_used": false` (все корабли, детерминированно; флаг смыслён только для `resurrection`). Ключи §7 не меняются и не удаляются — расширение назад-совместимо, `version: 1` сохраняется.
- В состояние добавлен верхнеуровневый `"dice": []` — журнал граней всех потреблённых кубиков по порядку (`rng_counter == dice.size()` — инвариант). Причина: со спец-правилами грани в потоке неоднородны (d6, d2, d4), и прежняя перемотка RNG «N раз d6» перестаёт восстанавливать позицию потока после snapshot/restore. Восстановление потока = повтор драфта + `next_die(grane)` по журналу. Альтернатива «журнал команд сам воспроизводит кубики» отвергнута: она требует полной реплея истории при каждом snapshot-restore.
- Кэш потока RNG в движке хранит `(seed, журнал граней, Rng)`; после боя кэш синхронизируется с полным журналом состояния. На детерминизм результата кэш не влияет (проверяется тестами: повтор из snapshot-копии и повторный прогон с нуля дают идентичные хеш и журнал).

### 8. Новые события (core-api §6, дополнение через этот ADR)

```text
ShipTransformed {ship_instance_id, from_type, to_type, hp, shield, charges}
ShipRevived    {ship_instance_id, hp}
```

`legal_actions` для активного корабля с `ranged_shot`: `DeclareAttack` на каждого живого врага в порядке массива `ships` (детерминированно); для остальных — без изменений (соседние враги в порядке `neighbors`).

## Последствия

- Тюнинг состояний тестами, golden-векторы hex/rng/canonical не затронуты; golden-replay матча seed 42 перегенерирован (см. «Миграция»).
- Боты и симуляции (BOTS-SIM) видят новые события, новые ключи состояния и возросшую длительность матчей (воскрешения/превращения продлевают игру до round_limit чаще); интерфейс `legal_actions` для не-Звезды Смерти не изменился.
- Совместное потребление кубиков героев (будущие C012+) обязано продолжать журнал `dice` и порядок §2.
- «Фантом» в драфте по-прежнему не участвует (`draftable: false`, группа 0).

## Миграция

Golden-файл `tests/golden/replay_seed_42.jsonl` регенерирован санкционированной процедурой: файл удалён, полный раннер `godot --headless --path . --script res://tools/run_tests.gd` записывает новый файл (ветка else в `tests/integration/test_random_match.gd`), второй прогон зелёный и сверяет hash. Старый golden описывал ruleset с выключенными способностями и несовместим с новыми правилами.

## Тесты

`tests/unit/test_engine_specials.gd` — на каждое правило позитивный и негативный сценарий (способность не срабатывает при невыполнении условия; отказ команды не мутирует состояние), порядок кубиков и `rng_index`, штраф −2/−4 на дистанциях 2/3, `legal_actions` для дальнобойного и ближнего атакующего, детерминизм «тот же seed + те же команды → тот же hash и журнал» для спец-матчей, snapshot round-trip состояний превращения и воскрешения (`revive_used`, d4-hp переживают restore с тем же hash).
