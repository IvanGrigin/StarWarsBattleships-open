# Тайминг и порядок разрешения — спринт 1 (минимальный боевой контур)

Статус: нормативный документ порядка операций. Числовые правила — `docs/rules/rules-v3.md`; норматив для кода — `docs/contracts/core-api.md` (§4–§9). Изменение порядка операций = новый ADR.

Область действия: только спринт-1 контур — драфт, расстановка, раунды/активации, заряды, соседний бой. Окна реакций героев и способности **вне контура спринта 1** (отключены, ADR-011); для них зарезервирована секция 9 без деталей. Особые правила кораблей тоже вне контура и реализуются отдельной задачей параллельно.

---

## 1. Общие принципы

1. **Детерминизм.** Единственный источник случайности — match-RNG mulberry32 (core-api §2). Порядок потребления RNG — часть правил: сначала весь драфт, затем бои в порядке объявлений (core-api §9). На `legal_actions` и snapshot RNG не тратится.
2. **rng_index.** Каждый вызов `next_die` получает порядковый номер с момента создания матча (счётчик с 0); номер записывается в событие `DieRolled`. (core-api §2, §6)
3. **Атомарность.** Одна применённая команда создаёт цепочку событий, но состояние меняется атомарно. Нелегальная команда возвращает `{"ok": false, "error": ...}`, **не меняет состояние и не создаёт событий**. (core-api §5)
4. **Формула силы** (core-api §4.4, зарезервирована на весь проект):

   ```text
   base die + sector arc + permanent passives + temporary statuses + range + reactions = final (min 0)
   ```

   В спринте 1 существуют только первые два слагаемых (`die + arc`); остальные равны 0.

## 2. Жизненный цикл матча

```text
MatchCreated → драфт (фаза draft) → расстановка → RoundStarted(1) → цикл раундов и активаций → MatchEnded
```

### 2.1. Создание

- `MatchCreated {ruleset_id, ruleset_hash, seed, round_limit}`; состояние получает фазу `draft`, `rng_counter: 0`, `round: 0`.
- Сиды назначаются `A1, B1, A2, B2`; команды `A = [A1, A2]`, `B = [B1, B2]`.

### 2.2. Драфт (фаза draft)

Порядок выбора: `A1, B1, A2, B2`, по 3 круга — 12 событий `ShipDrafted`. На каждом шаге:

1. Кандидаты — все типы `data/rulesets/v3/ships/*.json` с `draftable: true`, отсортированные по `id`.
2. Фильтр ограничений: 3 корабля на сид; бюджет `стоимость кандидата + текущая сумма ≤ 17 − минимальная сумма двух оставшихся разрешённых кораблей`; ≤ 1 корабль группы 2 на сид; корабли группы 2 уникальны в матче; один тип группы 1 — не более 2 у одного сида.
3. Выбор — единственное потребление RNG на шаге: `rng.next_below(n)` по отсортированному списку кандидатов.
4. Событие `ShipDrafted {seat, ship_instance_id, ship_type_id, cost}`.

Если допустимых кандидатов нет — ошибка конфигурации матча. (core-api §4.1)

### 2.3. Расстановка

- Берётся из `data/rulesets/v3/scenarios/classic_2v2.json`: i-й корабль сида (в порядке драфта) ставится на i-ю клетку списка; facing один на сид, в сторону центра. (core-api §8)
- События `ShipPlaced {ship_instance_id, q, r, facing, hp, shield, charges}` — в порядке сидов `A1, B1, A2, B2` и порядка драфта внутри сида. RNG не потребляется.
- Затем фаза становится `activation` и создаётся `RoundStarted {round: 1}`; активный сид — `A1`.

## 3. Раунд и порядок сидов

- Цикл сидов: `A1 → B1 → A2 → B2`.
- Раунд: каждый живой корабль активируется ровно один раз.
- После `EndActivation` ход передаётся **следующему в цикле сиду, у которого есть неактивированный живой корабль**; сиды без таких кораблей пропускаются. Пропуск сида **не создаёт событий** — он виден по тому, чей `ActivationStarted` или `RoundStarted` следует дальше.
- Если неактивированных живых кораблей нет ни у кого:
  - если `round + 1 ≤ round_limit` — `RoundStarted {round + 1}`, флаги `activated` сбрасываются;
  - если `round + 1 > round_limit` — `MatchEnded {winner: null, reason: "round_limit"}` (секция 6).

## 4. Активация: порядок внутри

1. `BeginActivation {ship_instance_id}` — проверки: фаза `activation`, свой сид, корабль жив и не активирован в этом раунде, другой активации не идёт. Успех → `ActivationStarted {seat, ship_instance_id, charges}`.
2. Действия выполняются в **любом порядке**, пока хватает ресурсов (rules-v3 §6): движение после атаки разрешено; атака не блокирует последующее движение/повороты.
   - `MoveForward` — 1 заряд: целевая клетка = соседняя по facing, свободна и в поле.
   - `RotateLeft` / `RotateRight` — 1 заряд: `facing = (facing ± 1) mod 6`, позиция не меняется.
   - `DeclareAttack {target_ship_instance_id}` — 0 зарядов, **не более 1 за активацию** (секция 5).
   - `EndActivation` — завершает активацию в любой момент; принудительных тайм-аутов в спринте 1 нет.
3. События успешного действия: **сначала** `ChargeSpent {ship_instance_id, reason: "move"|"rotate", charges_left}` (для действий с расходом), **затем** `ShipMoved` / `ShipRotated`. Событие расхода всегда предшествует событию результата.
4. Отклонённое действие (`no_charges`, `occupied_cell`, `out_of_board`, `attack_used`, `not_adjacent`, `bad_target`, `not_active_ship`, …) — без событий и без изменения состояния.
5. `EndActivation {}`:
   1. корабль восстанавливает **+1 заряд** до максимума 5 — **только** по `EndActivation`, даже если действий не было;
   2. `ActivationEnded {ship_instance_id, charges}` — `charges` указываются **после** восстановления;
   3. передача хода по секции 3 (следующий сид / `RoundStarted` / `MatchEnded`).

## 5. Порядок разрешения боя

Триггер — команда `DeclareAttack {target_ship_instance_id}` активного корабля.

0. **Проверки** (при отказе — `{"ok": false, ...}` без событий): фаза и сид; корабль активен и жив; цель — живой корабль **вражеской** команды на **соседнем** гексе; атака этой активации не израсходована.
1. `AttackDeclared {attacker_id, target_id}`.
2. **Сектора** (без бросков): `sector_att = sector_index(facing_att, direction_from(att_cell, tgt_cell))`; `sector_def = sector_index(facing_def, direction_from(def_cell, att_cell))` (core-api §1).
3. **Броски** из единственного match-RNG в строгом порядке: сначала атакующий `d6` (`DieRolled`, `role: "attacker"`), затем защищающийся `d6` (`role: "defender"`); каждое событие несёт `rng_index`.
4. **Силы** — спринт-1 подмножество формулы core-api §4.4 (`base die + sector arc`, остальные слагаемые 0): `strength = max(0, die + arc_modifiers[sector_index])`. Отрицательный модификатор обнуляет силу, но не делает её отрицательной. Затем `StrengthCalculated {ship_instance_id, die, sector_index, arc_bonus, total}` — сначала для атакующего, затем для защищающегося.
5. **Разность сил:** `diff = strength_att − strength_def`.
   - `diff > 0` — урон получает защищающийся;
   - `diff < 0` — урон получает атакующий (`|diff|`);
   - `diff = 0` — ничья, урона нет, **событие `DamageApplied` не создаётся**.
6. **Применение урона:** сначала снимается щит, остаток — здоровье; щит не восстанавливается никогда. `DamageApplied {target_id, shield_damage, hull_damage, hp_left, shield_left}`; `hp_left` не опускается ниже 0.
7. `hp ≤ 0` → `ShipDestroyed {ship_instance_id}`; корабль убирается с доски, уничтожение окончательно (воскрешение/превращение отключены до M2).
8. **Проверка конца матча** (секция 6) — после каждой применённой команды.

Примечание: в спринт-1 бою урон наносится ровно одной стороне, поэтому `both_eliminated` в одной цепочке недостижим; причина оставлена в контракте для полноты и будущих правил.

## 6. Конец матча

Проверяется после каждой применённой команды:

- У одной команды нет живых кораблей → `MatchEnded {winner: "<соперник>", reason: "elimination"}`.
- В одной атомарной цепочке опустели обе команды → `MatchEnded {winner: null, reason: "both_eliminated"}`.
- Все активации раунда исчерпаны и `round + 1 > round_limit` → `MatchEnded {winner: null, reason: "round_limit"}` (вместо `RoundStarted`).

После `MatchEnded` фаза `ended`; дальнейшие команды отклоняются с `wrong_phase`. Tie-breaker по оставшемуся HP в v3 не используется.

## 7. Сводка: команда → цепочка событий

| Команда | Цепочка событий (успех) |
|---|---|
| `BeginActivation` | `ActivationStarted` |
| `MoveForward` | `ChargeSpent(move)` → `ShipMoved` |
| `RotateLeft` / `RotateRight` | `ChargeSpent(rotate)` → `ShipRotated` |
| `DeclareAttack` | `AttackDeclared` → `DieRolled(att)` → `DieRolled(def)` → `StrengthCalculated` ×2 → (`DamageApplied` → (`ShipDestroyed`)) |
| `EndActivation` | `ActivationEnded` → (`RoundStarted`) или (`MatchEnded`) |
| отклонённая команда | событий нет |

Скобки — необязательные шаги (урон есть/нет; уничтожение; переход раунда/конец матча).

## 8. Согласование с примерами

`docs/rules/examples.md` следует порядку этой секции. Для читаемости `rng_index` в примерах указан локально (0, 1, … внутри примера); в реальном матче счётчик сквозной от `MatchCreated`.

## 9. ЗАРЕЗЕРВИРОВАНО (вне спринта 1, M2)

Этот раздел фиксирует только **место** будущих правил в порядке разрешения; детали будут определены отдельным документом/ADR в M2.

- **Окна реакций героев** — открываются в бою **после открытия бросков (шаг 3 секции 5) и до расчёта сил (шаг 4)**; соответствуют слагаемому `reactions` формулы core-api §4.4. Порядок разрешений реакций — по возрастанию `priority`, при равенстве — по порядку сидов.
- **Активные способности героев** — команда `UseHeroAbility` внутри активации; события `AbilityUsed`, `DieModified`, `MinePlaced`, `MineTriggered`, `BombAdvanced`.
- **Особые правила кораблей** — перебросы, воскрешение, превращение, дальний выстрел, спорные пассивки (rules-v3 §9.1–§9.5); слагаемые `permanent passives` / `temporary statuses` / `range` формулы.
- **Тайм-аут активации** с серверным `EndActivation`, сдача, bot takeover (rules-v3 §9.7).

Контракты способностей всех 8 героев уже зафиксированы данными (`data/rulesets/v3/heroes/*.json`, схема `data/schemas/hero.schema.json`) — движком спринта 1 не используются.
